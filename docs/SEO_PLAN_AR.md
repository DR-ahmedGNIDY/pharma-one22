## الملخص التنفيذي

الموقع مبني على Next.js 15 / React 19 (App Router) مع MongoDB عبر Mongoose، وصور على Cloudinary، ومصادقة NextAuth v5.

**الخبر الجيد:** طبقة الـ Metadata مبنية بشكل ممتاز فعلًا. صفحات المنتجات والبراندات تولّد عناوين وأوصاف وروابط Canonical و Open Graph فريدة من قاعدة البيانات، وكلها **تُرسل من السيرفر** (Server-Side). كما يوجد JSON-LD لـ Organization و WebSite و Product.

**الخبر السيئ:** ثلاث مشاكل هيكلية تُلغي معظم هذا العمل الجيد:

1. **ملف `robots.ts` يمنع الوصول إلى `/_next/`** — وهذا هو المسار الذي يقدّم منه Next.js كل ملفات JavaScript و CSS.
2. **كل صفحات المتجر (18 صفحة) هي `"use client"`** وتجلب بياناتها داخل `useEffect`. أي أن HTML القادم من السيرفر **لا يحتوي على اسم المنتج ولا السعر ولا الوصف ولا الصور**.
3. **لا توجد صفحات تصنيفات إطلاقًا.** التصنيفات موجودة فقط كـ query string على صفحة `/shop` المبنية بالكامل على العميل.

اجتماع المشكلتين ١ و ٢ يعني أن Googlebot يستقبل هيكل HTML فارغ، ولا يستطيع ملأه لأن السكريبت المطلوب لملئه **ممنوع بواسطة robots.txt**. هذه أخطر مشكلة في المشروع، وكل ما عداها ثانوي حتى تُحلّ.

## المشاكل الحرجة الأربع

### 🔴 ح-١ — robots.txt يمنع `/_next/` فيمنع Google من عرض الموقع

**المشكلة:** الملف يمنع المسار الذي تُقدَّم منه كل ملفات JS و CSS والصور المحسّنة.

**الدليل:**
```ts
disallow: ["/admin", "/admin/", "/account", "/account/", "/api/", "/_next/"],
```

**الموقع في الكود:** `app/robots.ts:12`

**التأثير:** خدمة العرض (Rendering) في Google تحتاج تحميل وتنفيذ ملفات JavaScript لترى المحتوى المبني على العميل. بمنع `/_next/` لا تستطيع تحميلها. وبما أن كل صفحة في المشروع مبنية على العميل (ح-٢)، فالنتيجة أن Google ترى **هيكلًا فارغًا للمتجر بأكمله**. كما يمنع `/_next/image` فتصبح مخرجات محسّن الصور غير قابلة للزحف — أي أن Google Images لا ترى شيئًا.

**الخطورة:** 🔴 حرجة (مانعة)

**الإصلاح:** حذف `/_next/` من قائمة المنع نهائيًا. الإبقاء على `/admin` و `/account` و `/api/`.

**الفائدة المتوقعة:** استعادة قدرة Google على عرض الصفحات أصلًا. هذا شرط مُسبق لكي يكون لأي إصلاح آخر في هذا التقرير أي أثر.

---

### 🔴 ح-٢ — 100% من الصفحات مبنية على العميل ولا توجد بيانات منتج في HTML السيرفر

**الدليل:** كل ملفات صفحات المتجر تبدأ بـ `"use client"`. وصفحة المنتج تحديدًا:
```tsx
"use client";
...
if (loading) {
  return <div ...>جاري تحميل المنتج...</div>;
}
```
أي أن جسم الـ HTML الذي يصل من السيرفر لصفحة `/product/<id>` هو حرفيًا النص "جاري تحميل المنتج…".

**الموقع في الكود:** `app/(shop)/product/[id]/page.tsx:1,95-101` — وكذلك `shop/page.tsx` و `brands/page.tsx` و `brand/[slug]/page.tsx` و `offers/page.tsx` و `home/page.tsx` وكل الصفحات الأخرى.

**ما هو غائب عن HTML الأولي:**

| العنصر | موجود في HTML السيرفر؟ |
| --- | --- |
| اسم المنتج | ❌ (موجود في `<title>` و JSON-LD فقط) |
| وصف المنتج | ❌ (موجود في `<meta>` و JSON-LD فقط) |
| السعر | ❌ (موجود في JSON-LD فقط) |
| `<h1>` | ❌ |
| الصور كـ `<img>` | ❌ |
| روابط Breadcrumb | ❌ |
| روابط المنتجات المشابهة | ❌ |

**عامل مخفِّف مهم:** دالة `generateMetadata` و JSON-LD الخاص بالمنتج **يُنفَّذان على السيرفر فعلًا** (داخل `layout.tsx` وهو Server Component). لذلك العنوان والوصف والبيانات المنظمة تصل إلى Google اليوم. هذا سبب أن الموقع لم يحصل على صفر، وهو تصميم جيد حقًا. لكن Metadata بلا محتوى مرئي مطابق هو تعارض تتعامل معه Google بريبة، ولا يمكنها ترتيب صفحة بناءً على محتوى لم ترَه أبدًا.

**الخطورة:** 🔴 حرجة

**الإصلاح:** تحويل `page.tsx` إلى Server Component يجلب المنتج مباشرة عبر Mongoose (بإعادة استخدام `getProduct` الملفوفة بـ `cache()` الموجودة في الـ layout المجاور)، ويعرض الاسم و H1 والسعر والوصف والصور و Breadcrumb والمواصفات من السيرفر — مع تفويض الأجزاء التفاعلية فقط (معرض الصور، الكمية، إضافة للسلة، المفضلة، التبويبات) إلى مكوّن `"use client"` صغير.

### 🔴 ح-٣ — لا توجد صفحات تصنيفات

**الدليل:** التصنيفات كيان كامل في قاعدة البيانات (`models/Category.ts` وبه `slug` و `description` و `image` و `parent` للتسلسل الهرمي) لكن **لا يوجد مسار `/category/[slug]`**.

```tsx
// components/sections/CategoriesSection.tsx:99
href={`/shop?category=${category.id}`}
```
```tsx
// components/layout/Header.tsx:36-41
{ name: "المكياج", href: "/shop?category=makeup" },
{ name: "العناية بالبشرة", href: "/shop?category=skincare" },
```
والفلترة تتم عبر خريطة أسماء عربية مكتوبة يدويًا وليس من قاعدة البيانات:
```tsx
// app/(shop)/shop/page.tsx:70-85
const catMap: Record<string, string> = {
  makeup: "المكياج", skincare: "العناية بالبشرة", ...
};
```

**التأثير:** صفحات التصنيفات هي **أعلى الصفحات قيمة تجارية** في أي استراتيجية SEO لمتجر إلكتروني — لأنها تستهدف الكلمات ذات أعلى حجم بحث ("مرطبات الوجه"، "كريم أساس"، "عطور نسائية"). هذا الموقع لديه **صفر** صفحات تستهدفها.

إضافة إلى ذلك: `/shop?category=X` ليس له Canonical خاص، ولا عنوان فريد، ولا H1 فريد، ولا وصف فريد. والفلترة تحدث على العميل بعد تحميل الكتالوج كاملًا، أي أن الرابط يُرجع HTML **مطابق تمامًا** لـ `/shop`. ستعتبرها Google كلها نسخًا مكررة من `/shop`.

وخريطة `catMap` خطر صيانة أيضًا: أي تصنيف يُضاف من لوحة التحكم لا يمكن الوصول إليه من القائمة.

**الخطورة:** 🔴 حرجة

### 🔴 ح-٤ — تعارض Canonical في الصفحة الرئيسية: `/` يحوّل إلى `/home`

**الدليل:**
```tsx
// app/page.tsx
export default function Page() { redirect("/home"); }
```
```tsx
// app/layout.tsx
alternates: { canonical: siteUrl },        // ← يشير إلى /
```
```ts
// app/(shop)/home/layout.tsx
alternates: { canonical: `${siteUrl}/home` },   // ← يشير إلى /home
```
وفي نفس الوقت شعار الهيدر و `navLinks[0]` يشيران إلى `/`:
```tsx
// components/layout/Header.tsx:35,181,199
{ name: "الرئيسية", href: "/" }
```

**التأثير:** ثلاث إشارات متعارضة حول ماهية الصفحة الرئيسية. كل رابط داخلي يشير إلى `/`، والذي يعمل تحويل **307 (مؤقت)** إلى `/home` — لأن `redirect()` داخل Server Component ليس تحويلًا دائمًا. وخريطة الموقع تُدرج `/home`. والروابط الخارجية وأي backlinks مستقبلية ستشير إلى `/`.

النتيجة: قوة الروابط (Link Equity) مُجزّأة عبر قفزة تحويل على **أهم رابط في النطاق بأكمله**. كما أن `/` غائب تمامًا عن خريطة الموقع.

**الخطورة:** 🔴 حرجة

## المشاكل عالية الأهمية 🟠

### ع-١ — متغير `NEXT_PUBLIC_SITE_URL` غير مضبوط

ملف `.env.local` يحتوي فقط على `CLOUDINARY_CLOUD_NAME` و `CLOUDINARY_API_KEY` و `CLOUDINARY_API_SECRET` و `MOCK_BRANDS`. و `.env.example` لا يذكر `NEXT_PUBLIC_SITE_URL` أصلًا. وتسعة ملفات تعتمد عليه:

```ts
const siteUrl = process.env.NEXT_PUBLIC_SITE_URL || "https://pharma-one.com";
```

**المواقع:** `app/layout.tsx:5`، `app/robots.ts:3`، `app/sitemap.ts:6`، `app/(shop)/product/[id]/layout.tsx:7`، `app/(shop)/brand/[slug]/layout.tsx:6`، وملفات layout لـ `shop` و `brands` و `offers` و `home`.

**التأثير:** إذا لم يكن نطاق الإنتاج هو `https://pharma-one.com` بالضبط، فإن **كل** وسم Canonical، و**كل** رابط في خريطة الموقع، وتوجيه `host` في robots.txt، وقيمتَي `@id` في JSON-LD، وحقول `url` في Organization و Product — كلها تشير إلى نطاق خاطئ. أي أنك تخبر Google أن النسخة المعتمدة من كل صفحة موجودة في مكان آخر.

**الخطورة:** 🟠 عالية — وترتفع إلى 🔴 حرجة إذا كان النطاق الحقيقي مختلفًا فعلًا.

### ع-٢ — الملفان `/og-image.jpg` و `/logo1.webp` غير موجودين (404)

مجلد `public/` يحتوي فقط على `icon.webp` و `images/` (وبداخله `logo1.webp` و `banners/panar2.webp` و `banners/panar5.webp`). لكن:

```tsx
// app/layout.tsx — openGraph.images
images: [{ url: "/og-image.jpg", width: 1200, height: 630, ... }]
// app/layout.tsx — twitter.images
images: ["/og-image.jpg"]
// app/layout.tsx — Organization JSON-LD
logo: { url: `${siteUrl}/logo1.webp`, width: 200, height: 60 }
```

ملف الشعار موجود فعليًا في `/images/logo1.webp` وليس `/logo1.webp`.

**التأثير:** كل مشاركة للصفحة الرئيسية أو المتجر أو البراندات أو العروض على واتساب أو فيسبوك أو X تظهر **بصورة معاينة مكسورة** — وهذا يخفض معدل النقر مباشرة، وهو مهم جدًا لجمهور مصري تُعد فيه المشاركة عبر واتساب قناة أساسية. وشعار Organization المكسور خطأ تحقق في Google Rich Results Test ويمنع ظهور الشعار في نتائج العلامة التجارية.

### ع-٣ — روابط المنتجات على واتساب مكسورة (خطأ وظيفي حقيقي)

المنتجات لديها حقل `slug` فريد في قاعدة البيانات، ودالة `slugify()` مكتوبة جيدًا تحافظ على الحروف العربية، ومسار API كامل `/api/products/slug/[slug]` — **ولا شيء من ذلك مستخدم في التوجيه**.

المسار الفعلي هو `/product/[id]` ويقبل ObjectId فقط. لكن رسالة واتساب في `ProductCard` تبني رابطًا بالـ slug:
```tsx
رابط المنتج:
${window.location.origin}/product/${product.slug}
```

بما أن المسار يتحقق بـ `Types.ObjectId.isValid` الذي يُرجع `false` لأي slug، فإن **كل رابط منتج يُشارَك عبر واتساب مكسور**. هذه مشكلة إيرادات مباشرة قبل أن تكون مشكلة SEO — وإصلاحها لا يستغرق أكثر من عشر دقائق.

### ع-٤ — نص التوفر مكتوب ثابتًا "متوفر في المخزن"

```tsx
// app/(shop)/product/[id]/page.tsx:272-275
<span className="flex items-center gap-1 text-green-400">
  <Check size={14} /> متوفر في المخزن ({product.stock} قطعة)
</span>
```

يُعرض دائمًا حتى عندما يكون `product.stock === 0` — فيظهر "متوفر في المخزن (0 قطعة)". بينما JSON-LD في نفس المجلد صحيح:
```ts
const availability = product.stock > 0 ? ".../InStock" : ".../OutOfStock";
```

**التأثير:** البيانات المنظمة تقول "غير متوفر" والصفحة المرئية تقول "متوفر". هذا بالضبط التعارض الذي تفحصه أنظمة جودة البيانات المنظمة في Google، وقد يؤدي إلى تعطيل Merchant Listings **على مستوى النطاق كله** وليس المنتج المتأثر فقط.

### ع-٥ — المنتجات غير النشطة تُقدَّم للعامة وقابلة للفهرسة

في `app/api/products/route.ts:116-143` كائن الفلترة **لا يتضمن `isActive` إطلاقًا**. والفرع غير المُصفَّح يُرجع `Product.find(filter)` بلا أي فحص. ومسار تفاصيل المنتج ومسار الـ slug كذلك. الملف الوحيد الذي يفلتر بشكل صحيح هو `app/sitemap.ts` (`Product.find({ isActive: true })`).

**النتيجة:** تناقض — Google تكتشف عبر الروابط الداخلية صفحات يقول الموقع نفسه في خريطته إنها يجب ألا توجد.

### ع-٦ — الصفحات المفقودة تُرجع HTTP 200 (Soft 404)

```tsx
// app/(shop)/product/[id]/page.tsx:103-109
if (!product) {
  return <div ...>المنتج غير موجود</div>;
}
```

لا يوجد استدعاء لـ `notFound()`، ولا يوجد `app/not-found.tsx` ولا `app/error.tsx`. الـ layout **يضبط `robots: { index: false }` بشكل صحيح** للمنتج المفقود — وهذا جيد — لكن الصفحة نفسها ترد بـ 200.

مع كتالوج 7000 منتج ومعدل تغيّر طبيعي، تتراكم أخطاء Soft 404 بسرعة في تقرير Page Indexing وتستهلك ميزانية الزحف.

### ع-８ — بيانات التقييمات موجودة ولا تُستخدم إطلاقًا

```ts
// models/Product.ts:44-45
rating: { type: Number, default: 0, min: 0, max: 5 },
reviewCount: { type: Number, default: 0 },
```
و `models/Review.ts` نموذج مراجعات كامل مع علامة شراء موثّق وربط بالطلب وفهرس فريد. لكن الصفحة تعرض:
```tsx
{activeTab === "reviews" && (
  <p className="text-gold-muted mb-4">التقييمات قريباً</p>
```

ولا يوجد `aggregateRating` في JSON-LD.

**التأثير:** النجوم في نتائج البحث من أعلى العوامل تأثيرًا على معدل النقر في التجارة الإلكترونية. النموذج مبني بالفعل — الميزة فقط غير موصولة.

**تنبيه مهم عند التنفيذ:** يجب إضافة `aggregateRating` **بشرط `reviewCount > 0`** فقط. إرسالها بقيمة `ratingValue: 0` مخالفة لسياسات البيانات المنظمة وقد تؤدي إلى إجراء يدوي. كما يجب إظهار التقييم بصريًا في الصفحة — Google تشترط أن يكون مرئيًا للمستخدم لا في الـ schema فقط.

## مشاكل الأداء 🔴

### أ-١ — ميزة "المنتجات المشابهة" تُنزّل الكتالوج بالكامل

```tsx
// app/(shop)/product/[id]/page.tsx:49-70
const loadSimilarProducts = async (categoryId: string) => {
  const res = await fetch("/api/products");        // ← كل المنتجات
  const data = await res.json();
  const filtered = data.products
    .filter((p) => p._id !== product?._id && p.category?._id === categoryId)
    .slice(0, 4);                                   // ← يحتفظ بـ 4 فقط
};
```
و `/api/products` بدون معامل `page` يُرجع كل شيء مع populate كامل:
```ts
// app/api/products/route.ts:133-143
if (!pageParam) {
  const products = await Product.find(filter).sort({ createdAt: -1 })
    .populate("brand").populate("category");
}
```

**التأثير:** لعرض **٤ منتجات مشابهة**، تنقل كل صفحة منتج كامل الـ 7000 منتج مع بيانات البراند والتصنيف. بتقدير متحفظ 1.5KB لكل منتج، هذا **حوالي 10 ميجابايت في كل زيارة صفحة**، بالإضافة إلى تكلفة تحليل JSON على الـ main thread، بالإضافة إلى استعلام MongoDB يُرجع المجموعة كاملة في كل تحميل.

هذا سيهيمن على INP، ويؤخر أي تفاعل لعدة ثوانٍ على الهاتف، وهو خطر جسيم على تكلفة واستقرار السيرفر.

**الملاحظة المهمة:** الـ API **يدعم بالفعل** `?page=&limit=` و `?category=` — الإصلاح هو ببساطة استخدامهما.

### أ-٢ — صفحة المتجر تفعل الشيء نفسه

`app/(shop)/shop/page.tsx:50-62` تستدعي `fetch("/api/products")` بلا تصفيح، ثم تُصفّح في الذاكرة (`sortedProducts.slice(0, visibleCount)`). وخيارات الفلاتر مشتقة على العميل بـ `Set` من المصفوفة الكاملة.

أي أن زر "عرض المزيد" هو مجرد تقطيع لبيانات **مُحمَّلة بالفعل** — لا يوفر أي فائدة شبكية على الإطلاق.

### أ-٣ — `framer-motion` داخل كل بطاقة منتج

`ProductCard.tsx` يلف كل بطاقة في `<motion.div initial animate whileInView viewport>`. مع شبكة من 24 بطاقة، ينشأ 24 اشتراك IntersectionObserver للحركة. على أجهزة أندرويد متوسطة الفئة — وهي الفئة الغالبة لهذا الجمهور — هذه تكلفة مباشرة على INP و TBT.

- بنية `generateMetadata` من السيرفر — **صحيحة تمامًا**

### ملاحظة على المهمة ٢٩ — جودة عناوين المنتجات

```ts

```

الضعف ليس في القالب بل في **البيانات المصدر**: `Product.name` نص حر يُدخله المسؤول بلا أي إرشاد أو تحقق. لا شيء يمنع اسمًا مثل "كريم".

| ضعيف | أفضل |
| --- | --- |
| `كريم` | `كريم مرطب للوجه للبشرة الجافة 50 مل - CeraVe` |

### تفصيل مشكلة الخطوط (المهمة ٢٢)

`styles/globals.css:5` يحتوي على استيراد خطوط Google:
```css
@import url('https://fonts.googleapis.com/css2?family=Noto+Sans+Arabic:...');
```
لكن `app/layout.tsx:2` يستورد `./globals.css` — وهو **ملف مختلف تمامًا**! وتعليق داخل الملف يؤكد ذلك: `/* previously defined only in the unused styles/globals.css */`. و`app/globals.css:21` يضبط `font-family: sans-serif`.

بينما Tailwind يعرّف `font-arabic: ["Noto Sans Arabic", "Tajawal", "sans-serif"]` و`<body>` يحمل `className="font-arabic"` — فيتحول إلى خط النظام الافتراضي لأن أيًا من الخطين غير مُحمَّل.

**الأثر مزدوج:**
- ✅ **إيجابيًا:** الموقع يتجنب ثلاثة طلبات خطوط حاجبة للعرض عبر 20+ وزنًا — وهي تكلفة LCP خطيرة
- ❌ **سلبيًا:** نظام التصميم العربي بأكمله يُعرض بخط نظام عام، و`Playfair Display` يتحول بصمت إلى `serif`

**الحل:** تحميل الخطوط عبر `next/font/google` مع `subsets: ["arabic"]` و`display: "swap"` و**الأوزان المستخدمة فعليًا فقط (2–3 أوزان)**. هذا يستضيفها ذاتيًا ويزيل الاتصال بطرف ثالث ويلغي خطر CLS/FOUT الذي كان سيسببه `@import`. ثم حذف `styles/globals.css` غير المستخدم.

### ملاحظة على `initialScale: 0.85`

```tsx
export const viewport = { width: "device-width", initialScale: 0.85 };
```
يعرض الصفحة بمقياس 85% عند التحميل، فيُصغّر كل النصوص عن حجمها المُصمَّم بنحو 15%. المعيار هو `1`. (ملاحظة إيجابية: `maximumScale` و `userScalable` مُترَكان دون ضبط بشكل صحيح — أي أن التكبير باللمس يعمل.)

```
التحقق عبر URL Inspection أن ملفات JS تُحمَّل
   ↓
إصلاح ح-٢ (العرض من السيرفر)
   ↓
إعادة الفحص
   ↓
عندها فقط: إرسال خريطة الموقع + طلب فهرسة عينة من الروابط
```

**إرسال خريطة بـ 7000 رابط لصفحات غير قابلة للعرض أولًا** سيستهلك ميزانية الزحف ويؤسس إشارة جودة سيئة تحتاج وقتًا للتعافي منها.

## 🟢 المرحلة السابعة — Merchant Center (مؤجلة)

**التقييم الصريح: هذه ليست الاستثمار الصحيح التالي لهذا المشروع.**

### العوائق الأساسية خارج الكود

**١. لا يوجد Checkout على الموقع.** الطلب يتم عبر واتساب (`createWhatsAppLink` في `lib/utils.ts`). و Google Merchant Center يشترط عمومًا وجود عملية دفع فعّالة — مسار واضح من صفحة المنتج إلى شراء مكتمل بتكلفة إجمالية ظاهرة. تدفّق يعتمد على واتساب وحده **من المرجح جدًا أن يفشل في المراجعة**. هذا **قرار نموذج عمل، لا إصلاح برمجي**، ويجب حسمه قبل الاستثمار في هندسة الـ feed.

**٢. GTIN أو MPN إلزامي عمليًا.** لمنتجات التجميل ذات العلامات التجارية التي لها باركود من المصنّع، يشترط Merchant Center حقل `gtin`. بدونه تُرفض المنتجات أو تُخفَّض أولويتها بشدة.

إضافة `gtin13` إلى `models/Product.ts` ولوحة التحكم **تغيير برمجي صغير**؛ لكن **جمع 7000 باركود من الموردين هو المشروع الحقيقي**. ابدأ بالمنتجات الأعلى مبيعًا.

**٣. صفحات السياسات المطلوبة:**

| الصفحة | الحالة |
| --- | --- |
| سياسة الاسترجاع `/return-policy` | ✅ موجودة |
| سياسة الشحن `/shipping` | ❌ **مرتبطة ولا توجد** |
| طرق الدفع `/payment-methods` | ❌ **مرتبطة ولا توجد** |
| التواصل `/contact` | ✅ موجودة |
| الشروط `/terms` | ✅ موجودة |

اثنتان من خمس روابط مكسورة. (تُبنيان في المرحلة الرابعة.)

**٤. حساب Merchant Center** — الإنشاء وتوثيق النشاط ومطالبة الموقع وإعدادات الشحن والضرائب واستهداف السوق المصري، كلها إعدادات خارجية.

**٥. البيانات المنظمة وحدها لا تُنتج Merchant Listings.** الـ Schema تساعد Google على فهم الصفحة وقد تُفعّل القوائم المجانية، لكن أسطح Shopping المدفوعة تتطلب الـ feed وحسابًا معتمدًا. والأهم: schema تصف محتوى غير مرئي هي **عبء لا أصل**.

### معمارية الـ Feed عند الوصول لهذه المرحلة

```
app/feed/google-merchant.xml/route.ts   → RSS 2.0 بمساحة الأسماء g:
```

استعلام `Product.find({ isActive: true, stock: { $gt: 0 } })` مع populate للبراند والتصنيف، وبثّ XML، وتخزين مؤقت بـ `revalidate`. هذا يبقي الـ feed **متزامنًا تلقائيًا** مع الكتالوج — بلا تصدير CSV ولا رفع يدوي.

**لا تبنِ بديل CSV** — الـ XML بنفس الجهد ويُحدّث نفسه.

### جاهزية الحقول

| الحقل المطلوب | متوفر | المصدر |
| --- | --- | --- |
| `id` | ✅ | `_id` أو `sku` |
| `title` | ✅ | `name` |
| `description` | ✅ | `description` |
| `link` | ✅ | رابط المنتج المعتمد |
| `image_link` | ✅ | `images[0]` |
| `additional_image_link` | ✅ | `images[1..10]` |
| `availability` | ✅ | مشتق من `stock` |
| `price` / `sale_price` | ✅ | `price` / `discountPrice` |
| `brand` | ✅ | `brand.name` |
| `condition` | ✅ | ثابت `new` |
| **`gtin`** | ❌ | **لا يوجد حقل** |
| **`mpn`** | ❌ | **لا يوجد حقل** |
| `google_product_category` | ❌ | يحتاج ربط بتصنيفات Google |
| `shipping` | ❌ | لا توجد بيانات شحن في المشروع |

**التوصية:** الفهرسة العضوية للمنتجات والتصنيفات (المراحل ١–٣) تعطي قيمة أعلى بكثير لكل وحدة جهد. عُد إلى Merchant Center بعد وجود Checkout وتوفر GTIN.

## 🟡 المرحلة الثامنة — استراتيجية المحتوى

**المدة:** مستمرة، 3–6 أشهر · **هنا يأتي النمو المُركَّب**

### الطبقة ١ — محتوى التصنيفات (الأولوية القصوى)

150–300 كلمة مفيدة فعلًا لكل تصنيف، **أسفل شبكة المنتجات** حتى لا تدفع المنتجات لأسفل.

مثال لـ "مرطبات الوجه": ما وظيفة المرطب، كيف تختارينه حسب نوع البشرة، المكونات التي تبحثين عنها، ترتيب التطبيق. **مكتوب لعميلة، لا لمحرك بحث.**

### الطبقة ٢ — معايير وصف المنتجات

إعادة صياغة نصوص المورّد في بنية موحدة:
```
ما هو → لمن يناسب → المكونات الأساسية → طريقة الاستخدام → الحجم والشكل
```

**لماذا هذا مهم:** نسخ وصف المصنّع مشكلة شبه عامة في تجارة التجميل. كل منافس يبيع نفس منتج CeraVe لديه على الأرجح **نفس النص حرفيًا**. Google تدمج هذه الصفحات وتختار واحدة — عادة صاحبة السلطة الأعلى. هذا هو السبب الرئيسي لفشل صفحات المنتجات في الترتيب في هذا المجال.

حتى إعادة صياغة خفيفة تكسر هذا الدمج.

**رتّب الأولويات:** أفضل 200 منتج حسب هامش الربح أو إمكانية جلب الزيارات — لا تحاول 7000 منتج.

### الطبقة ٣ — المحتوى المعرفي `/blog/[slug]`

| المقال | يربط إلى |
| --- | --- |
| أفضل مرطب للبشرة الجافة | `/category/moisturizers` + منتجات محددة |
| كيفية اختيار مرطب الوجه المناسب لنوع بشرتك | `/category/moisturizers` |
| الفرق بين السيروم والمرطب والكريم | تصنيفات متعددة |
| ترتيب روتين العناية بالبشرة الصحيح | التسلسل الكامل للعناية |
| أفضل واقي شمس للوجه في مصر | `/category/sunscreen` |
| كيف تعرفين المنتج الأصلي من المقلد | `/about` وصفحات البراندات — قيمة ثقة عالية في هذا السوق |

**لماذا هذه الطبقة مهمة:** في مجال التجميل بالعربية، **الاستعلامات المعرفية تحمل حجم بحث أكبر بكثير من التجارية**، وهي المدخل الذي يدخل منه معظم العملاء إلى القمع البيعي.

### الطبقة ٤ — محتوى تحريري للبراندات

150 كلمة لكل براند عن موقعه ومنتجاته الأبرز. جهد منخفض، وصفحات البراندات هي أكثر أصول الموقع جاهزية للترتيب.

### ❌ تجنّب صراحةً

- قوالب أوصاف مولّدة آليًا تتغير فيها كلمة الاسم فقط (Google تكتشفها وتخفض قيمتها)
- حشو الكلمات المفتاحية في نصوص التصنيفات
- صفحات مدخل رقيقة لكل تنويعة كلمة مفتاحية

جودة النصوص العربية الحالية تُثبت أن الفريق يكتب جيدًا — القيد هو الكم، لذا رتّب الأولويات بصرامة.

## استراتيجية الكلمات المفتاحية

مستخرجة من التصنيفات في `Header.tsx` والبراندات المذكورة في الـ metadata.

### كلمات المنتجات ← صفحات المنتجات
النمط: `{اسم المنتج} + {البراند} + {الحجم}`
- `كريم مرطب سيرافي 50 مل`
- `سيروم فيتامين سي ذا اورديناري`
- `فاونديشن ماك استوديو فيكس`

حجم منخفض فرديًا، لكن **نية شرائية عالية جدًا ومنافسة منخفضة**. مع 7000 منتج، هذا هو محرك حجم الذيل الطويل — ويعتمد كليًا على قابلية فهرسة صفحات المنتجات (ح-١/ح-٢).

### كلمات التصنيفات ← صفحات `/category/[slug]` الجديدة
- `مكياج اون لاين مصر` ← `/category/makeup`
- `منتجات العناية بالبشرة` ← `/category/skincare`
- `مرطبات الوجه` ← `/category/skincare/moisturizers`
- `عطور نسائية أصلية` ← `/category/perfumes`
- `واقي شمس للوجه` ← `/category/skincare/sunscreen`

أعلى حجم، أعلى منافسة. **الموقع حاليًا لا يملك أي صفحة تستطيع استهداف أي منها.**

### الكلمات التجارية ← التصنيفات والعروض
`شراء كريم مرطب اون لاين` · `اسعار مكياج في مصر` · `عروض منتجات التجميل` · `متجر مستحضرات تجميل اصلية`

### الكلمات المعرفية ← `/blog/[slug]`
`أفضل كريم للبشرة الجافة` · `كيفية اختيار مرطب الوجه` · `الفرق بين المرطب والكريم` · `فوائد فيتامين سي للبشرة`

### كلمات البراندات ← `/brand/[slug]`
`سيرافي مصر` · `ذا اورديناري مصر` · `منتجات لوريال الاصلية` · `{البراند} + اسعار`

**فرصة قوية:** حجم متوسط، منافسة منخفضة، نية عالية — وصفحات البراندات أقرب ما لديك لقالب جاهز للترتيب.

### كلمات الدفاع عن العلامة ← الصفحة الرئيسية
`فارما وان` · `Pharma One Cosmetics` · `فارما وان كوزماتيكس`

**مُعطَّلة حاليًا** بسبب تعارض `/` و `/home` (ح-٤).

### جدول الربط

| نوع الكلمة | الصفحة المستهدفة | موجودة؟ |
| --- | --- | --- |
| الدفاع عن العلامة | `/` | ⚠️ منقسمة مع `/home` |
| التصنيف | `/category/[slug]` | ❌ |
| التصنيف الفرعي | `/category/[slug]/[sub]` | ❌ |
| البراند | `/brand/[slug]` | ✅ (تحتاج SSR) |
| المنتج | `/product/[slug]` | ⚠️ (ObjectId + CSR) |
| التجارية | `/offers` والتصنيفات | ⚠️ جزئي |
| المعرفية | `/blog/[slug]` | ❌ |

> **ملاحظة واقعية:** استخراج الكلمات من الكود يحدد **المحاور** لا **الأحجام**. هذه فرضيات. تحقق منها عبر Google Keyword Planner وبيانات استعلامات Search Console بعد نجاح الفهرسة، والإكمال التلقائي بالعربية مع استهداف مصر — قبل تخصيص ميزانية محتوى.

```
    │   ├── layout.tsx                  metadata + Breadcrumb + ItemList
```

## ⚠️ ما لا يستطيع هذا التقرير أن يَعِد به

**إصلاح كل ما في هذه الخطة لن يضمن الظهور في الصفحة الأولى** — وأريد أن أكون صريحًا في هذه النقطة.

الـ SEO التقني يجعل الموقع **مؤهلًا** للترتيب؛ لا يحدد **موقعه**. الترتيب الفعلي يعتمد على:

- **المنافسة** — سوق التجميل الإلكتروني في مصر يضم لاعبين راسخين ومموّلين جيدًا
- **الروابط الخلفية وسلطة النطاق** — لا شيء في هذا التقرير يؤثر عليهما؛ تُكتسب عبر العلاقات العامة والشراكات والمحتوى الجدير بالربط
- **قوة العلامة التجارية** — حجم البحث عن اسمك هو نفسه إشارة ترتيب، تُبنى بالتسويق لا بالكود
- **جودة المحتوى وعمقه** مقارنة بما يحتل الترتيب حاليًا
- **مطابقة نية البحث** — قد تفضّل Google الأسواق الكبيرة أو المحتوى المعرفي لاستعلام معين بغض النظر عن تحسيناتك
- **حجم الطلب البحثي** — بعض الكلمات المستهدفة قد يكون حجمها أقل من المفترض حتى التحقق ببيانات حقيقية
- **العوامل الجغرافية والتخصيص**
- **أنظمة Google** التي تتغير باستمرار وليست معروفة بالكامل

**ما يحققه هذا العمل بشكل موثوق:** إزالة الحواجز التي تمنع Google حاليًا من رؤية الموقع أصلًا، ووضع المتجر في موضع يستطيع فيه المنتج الجيد والمحتوى الجيد أن ينافسا فعلًا.

الموقع حاليًا **لا يخسر أمام المنافسين على أساس الجدارة — بل هو غير مرئي لأسباب هيكلية.** وهذه مشكلة قابلة للحل، وهي المشكلة الصحيحة التي يجب البدء بها.

## التوصيات النهائية

1. **نفّذ المهمة رقم ١ اليوم.** حذف `/_next/` من robots.txt تعديل سطر واحد يفتح الطريق لكل ما عداه. لا يوجد سبب لتأجيله خلف أي شيء.
2. **تحقق من `NEXT_PUBLIC_SITE_URL` فورًا.** إذا لم يكن نطاق الإنتاج `pharma-one.com`، فكل رابط canonical وكل رابط في خريطة الموقع خاطئ الآن — وهذه مشكلة صامتة وخطيرة.
3. **العرض من السيرفر هو المشروع الحقيقي.** المهام ٥ و٦ و٧ و١٣ تمثل معظم الجهد ومعظم القيمة. كل ما عداها ضبط دقيق.
4. **ابنِ صفحات التصنيفات.** غياب أي صفحة تصنيف هو أكبر فرصة ضائعة في هذا المشروع، ونموذج البيانات يدعمها بالفعل.
5. **لا تلاحق Merchant Center الآن.** عائق الـ Checkout أساسي ولا يمكن الالتفاف عليه هندسيًا.
6. **حافظ على ما هو جيد بالفعل.** بنية `generateMetadata`، واستخدام `cache()`، وإعداد `next/image`، وغياب سكريبتات الطرف الثالث، وجودة النصوص العربية — كلها فوق مستوى القطاع. إصلاحات هذا التقرير يجب أن **تمتد على هذا العمل لا أن تستبدله**.
7. **قِس قبل وبعد.** أنشئ خط أساس في Search Console بعد المرحلة الأولى وقبل الثانية، حتى يكون أثر عمل العرض من السيرفر قابلًا للنسبة.
